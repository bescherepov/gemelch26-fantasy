# Концепция сайта «Расфадаль. Мир. Хроника»

**Единый источник информации + GitHub Actions + GitHub Pages.**
Версия 1.1 · октябрь 2026 · репозиторий `bescherepov/gemelch26-fantasy`
Сайт: <https://bescherepov.github.io/gemelch26-fantasy/>

---

## 1. Коротко

Сайт — спутник текстовой партии «Гегемония» о мире Расфадаля (900–910 гг.). Задача сайта: показывать мир, народы, историю и ходы так, чтобы игроку было удобно, а мастеру — дёшево обновлять.

Ключевое решение: **ни одна страница не пишется руками**. Есть один каталог `data/*.json` — единственный источник информации (SSOT). Из него скрипт `build.py` собирает статический сайт, а GitHub Actions проверяет данные, собирает страницы и публикует их на GitHub Pages.

```text
data/*.json ──► validate ──► build.py ──► dist/ ──► GitHub Pages
     ▲                          ▲
     │                          │
  правка в git            GitHub Actions
```

Что это даёт:

| Было (старый сайт) | Стало |
| --- | --- |
| Данные зашиты в JS-файлы на 70–220 КБ | Данные — в маленьких JSON-файлах по темам |
| Одно событие правится в 2–3 местах | Одно событие — одна запись |
| Лог изменений ведётся вручную | Лог собирается из истории git |
| Ошибку видит игрок | Ошибку ловит CI до публикации |
| Нет предпросмотра | PR получает собранный артефакт |
| Публикация — пуш в ветку сайта | Публикация — стандартный Pages-деплой |

Текущий объём: **3 хода, 36 событий, 9 народов, 4 карты, 136 построек, 11 страниц**. Сборка — меньше секунды, зависимостей — ноль.

## 2. Наследие старого сайта

### 2.1 Что было

Старый сайт (`dipaeu26`, партия «Европа 1150») — набор статических HTML-страниц с общим `style.css` и большими JS-файлами данных:

| Файл | Размер | Что внутри |
| --- | --- | --- |
| `turns.js` | 223 КБ | события всех ходов |
| `buildings.js` | 86 КБ | постройки + логика таблицы |
| `innovation.js` | 72 КБ | инновации |
| `distance.js` | 29 КБ | координаты городов и считалка |
| `players.js` | 22 КБ | статистика 42 стран |
| `tables-script.js` | 8 КБ | переключатель таблиц |
| `style.css` | 5,7 КБ | единый стиль |
| `01concepts.html` … `14HRE.html` | 14 страниц | правила |
| `turns/turn00.html` … `turn15.html` | 16 файлов | тексты ходов |

Плюс 7 карт, ~34 изображения таблиц и ручной `log.html` на полсотни записей.

### 2.2 Что стоит сохранить

- **Статический хостинг.** Никаких серверов, баз и оплаты — GitHub Pages.
- **Архивный вид.** Олива, янтарь, бумага, серифная типографика — сайт читается как летопись, а не как дашборд.
- **Разделы.** Ходы, карты, таблицы, ссылки, лог — привычная навигация для игроков.
- **Переключатели.** Идея «одна страница — много ходов/карт» удобна и перенесена.
- **Git как хранилище.** История, откат, авторство — всё уже есть.
- **Лог изменений.** Игроки привыкли видеть, что и когда обновилось.

### 2.3 Что стоило переделать

1. **Данные внутри кода.** Чтобы поправить одно событие, нужно открыть 223-килобайтный `turns.js` и не сломать синтаксис.
2. **Дублирование.** Событие живёт в `turns.js` и в `turns/turnNN.html`; карта — в `maps.html` и в `map-script.js`. Расхождение почти неизбежно.
3. **Ручной лог.** Забытая запись — обычное дело; технические правки попадают в игровой лог.
4. **Нет проверок.** Битая ссылка, опечатка в `id`, потерянная картинка обнаруживаются игроком.
5. **Единственная автоматизация.** `dev/xlsx2js.py` генерирует только `buildings.js`; остальное — руками.
6. **Нет предпросмотра.** Изменение видно только после публикации.
7. **Ходы копируются файлами.** Каждый новый ход — это новый HTML-файл и правка навигации.

Вывод: проблема не в статике как таковой, а в том, что **контент и представление перемешаны**. Лечится не фреймворком, а разделением данных и шаблонов.

## 3. Принцип: единый источник информации

### 3.1 Поток данных

```text
  Источники мастера                         Репозиторий                        Продакшн
  ─────────────────                         ───────────                        ────────
  DM.AM: хроника партии ─┐
  Setting.docx          ├─► перенос ──► data/*.json ──► validate.py ──┐
  2_khod_905.docx       │   в JSON          │                         │
  3_khod_910.docx      ─┘                   │                         ├─► build.py ─► dist/ ─► GitHub Pages
  карты *.png ─────────► assets/img ────────┘                         │
                                                                       └─► changelog.py ◄─ git log
```

Правила, на которых держится схема:

1. **Один факт — одна запись.** Событие хода описано только в `data/turns/NNN.json`. Оно не дублируется ни в шаблоне, ни в логе, ни в навигации.
2. **Страницы — производные.** HTML в `dist/` не редактируется и не коммитится. Ручная правка `dist/` будет затёрта следующей сборкой.
3. **Источник — текст, а не вёрстка.** В JSON лежат заголовки, тексты, даты, ссылки на изображения. Оформление — в шаблонах и CSS.
4. **Ссылки на файлы, а не копии.** Карта хранится один раз в `assets/img`, а в данных — путь к ней. Валидатор проверяет, что файл существует.
5. **Изменение атомарно.** Новый ход — это один JSON-файл, один файл карты и одна запись в `maps.json`. Всё в одном коммите.
6. **Проверка до публикации.** Если данные не сходятся, CI падает и сайт не обновляется.

### 3.2 Граница ответственности

| Слой | Где | Кто меняет | Что можно |
| --- | --- | --- | --- |
| Контент | `data/` | мастер / редактор | тексты, даты, события, ссылки |
| Изображения | `assets/img/` | мастер / редактор | карты, таблицы |
| Представление | `templates/`, `assets/css`, `assets/js` | разработчик | вёрстка, стиль, интерактив |
| Сборка | `build.py`, `engine.py`, `scripts/` | разработчик | правила генерации и проверок |

Эта граница — главное практическое следствие концепции: редактору не нужно знать HTML, а разработчику не нужно трогать контент.

## 4. Модель данных

### 4.1 Состав

| Файл | Что описывает | Ключевые поля |
| --- | --- | --- |
| `site.json` | название, подпись, меню, базовый URL, период | `title`, `tagline`, `menu[]`, `base_url`, `period` |
| `world.json` | мир: вступление, факты, регионы, законы | `lead`, `intro[]`, `facts[]`, `regions[]`, `laws[]` |
| `history.json` | летопись 400–900: эпохи, битвы, герои | `epochs[].blocks[]`, `battle`, `heroes[]` |
| `ethnoses.json` | девять народов | `id`, `color`, `epithet`, `analog`, `geography`, `description`, `status` |
| `turns/NNN.json` | один ход: год, название, карта, события | `number`, `year`, `title`, `lead`, `map`, `events[]` |
| `maps.json` | каталог карт и разделов | `categories[]`, `maps[].file` |
| `tables.json` | игровые таблицы | `tables[].file` |
| `buildings.json` | постройки и местные правила | `buildings[].id`, `changes[].id` |
| `participants.json` | рассадка | `count`, `image`, `notes[]` |
| `links.json` | внешние ссылки | `links[].url` |
| `changelog.json` | лог изменений | `entries[].date`, `text` |

### 4.2 Как выглядит ход

```json
{
  "number": 3,
  "year": 910,
  "title": "Кашшу",
  "lead": "В мире появляется первая организованная религия…",
  "map": {
    "image": "assets/img/map-political-905.png",
    "caption": "Политическая карта после 2-го хода (905 г.)"
  },
  "events": [
    {
      "type": "religion",
      "title": "Кашшу",
      "text": "Деятельность расфадальского священника Линуса Даре…"
    }
  ]
}
```

Тип события — из закрытого списка: `politics`, `war`, `diplomacy`, `dynasty`, `religion`, `disaster`, `economy`, `city`, `culture`, `migration`. Тип задаёт бейдж, цвет и фильтр на странице ходов. Новый тип добавляется в одном месте — `TYPE_LABELS` в `build.py`, — и валидатор сразу требует, чтобы он был известен.

### 4.3 Как выглядит народ

```json
{
  "id": "soravians",
  "name": "Соравийцы",
  "color": "#2e5f8f",
  "epithet": "Северные владыки морей и фьордов",
  "analog": "Скандинавы / викинги",
  "geography": "Суровый северный регион…",
  "description": "Воинственный морской народ…",
  "status_label": "Экспансия",
  "status": "Продвигаются на юг…"
}
```

`color` — канонический цвет народа с карты этносов; он же используется в акцентах карточки. `status` может быть `null` — шаблон это учитывает.

### 4.4 Инварианты

Валидатор (`scripts/validate.py`) проверяет:

- номера ходов идут подряд с 1, годы строго возрастают и не повторяются;
- у каждого события известный тип и непустые заголовок и текст;
- `id` уникальны внутри коллекций (народы, эпохи, карты, ссылки);
- цвета в формате `#rrggbb`;
- все упомянутые изображения существуют;
- категории карт объявлены;
- даты лога в формате `ГГГГ-ММ-ДД`;
- пункты меню ведут на реально собираемые страницы;
- в собранном сайте каждая страница имеет один `<h1>`, непустые `<title>` и `meta description`, а все внутренние ссылки и якоря разрешаются.

Ошибка формулируется человеческим языком и указывает файл и поле:

```text
turns/915.json → events[4]: неизвестный тип события «sea»
maps.json → maps[2]: нет файла assets/img/map-915.png
```

## 5. Сборка

### 5.1 `build.py`

Один скрипт, стандартная библиотека, детерминированный результат:

1. читает `data/*.json` и `data/turns/*.json`;
2. проверяет существование изображений;
3. обогащает данные производными полями (подписи типов, счётчики, превью);
4. рендерит страницы шаблонами;
5. копирует `assets/` в `dist/`;
6. пишет `sitemap.xml`, `robots.txt`, `.nojekyll`, `404.html`;
7. печатает сводку: `Собрано: 11 страниц, 3 хода, 36 событий…`.

`dist/` каждый раз создаётся заново. Это гарантирует, что в публикацию не попадёт забытый файл.

### 5.2 Движок шаблонов

`engine.py` — минимальный движок на ~360 строк, чтобы не тащить Jinja2 и не превращать сайт в Node-проект:

| Возможность | Синтаксис |
| --- | --- |
| Подстановка с экранированием | `{{ event.title }}` |
| Готовый HTML | `{{ content \| safe }}` |
| Цикл | `{% for e in turn.events %} … {% endfor %}` |
| Условие | `{% if turn.map %} … {% elif … %} … {% else %} … {% endif %}` |
| Вложенный шаблон | `{% include "partial.html" %}` |
| Метаданные цикла | `loop.index`, `loop.first`, `loop.last`, `loop.length` |
| Фильтры | `date_ru`, `length`, `join`, `default`, `upper`, `lower`, `number` |

Обращение к несуществующему ключу в `{{ … }}` — ошибка сборки: опечатка в имени поля не превратится в пустое место на странице. В условиях (`{% if epoch.outro %}`) отсутствующий ключ считается пустым — так работают необязательные поля.

Автоэкранирование включено по умолчанию, поэтому текст из данных не может сломать вёрстку.

### 5.3 Детерминизм

- нет сети, таймеров и случайности;
- даты сборки можно зафиксировать переменной `SOURCE_DATE_EPOCH` (используется в CI при необходимости);
- сортировка ходов — по номеру, лога — по дате, карт — по порядку в файле;
- одинаковый вход даёт одинаковый выход — удобно для диффов и кеша.

### 5.4 Тесты

`tests/` — 36 тестов на стандартном `unittest`, без pytest:

- `test_engine.py` проверяет движок: экранирование, `safe`, циклы с `loop`, условия, `elif`, отсутствующие ключи, фильтры, `include`, ошибки разбора;
- `test_build.py` собирает сайт и проверяет, что все страницы на месте, в HTML не осталось `{{ }}`, sitemap полон, а `validate.py --dist` проходит.

Тесты идут в CI перед публикацией: сломанный шаблон или генератор не доедет до продакшна.

## 6. GitHub Actions

### 6.1 Триггеры

| Событие | Что происходит |
| --- | --- |
| `push` в `main` | проверка → тесты → сборка → публикация |
| `pull_request` | проверка → сборка → артефакт `site-preview` (без публикации) |
| `workflow_dispatch` | ручной запуск |
| `schedule` (по понедельникам) | плановая пересборка: подтягивает свежие записи лога из git |

### 6.2 Джобы

```yaml
jobs:
  build:   # ubuntu-latest, Python 3.12, ~1 минута
    - actions/checkout@v4 (fetch-depth: 0)
    - actions/setup-python@v5
    - python scripts/validate.py
    - python -m unittest discover -s tests
    - python scripts/changelog.py
    - python build.py
    - python scripts/validate.py --dist
    - actions/upload-pages-artifact@v3  (dist)
    - actions/upload-artifact@v4        (только для PR)

  deploy:  # только main, после build
    - actions/deploy-pages@v4
```

`fetch-depth: 0` нужен, чтобы `changelog.py` видел всю историю коммитов по `data/`, а не только последний.

### 6.3 Права и окружение

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

Публикация идёт через OIDC-токен GitHub Pages — никаких персональных токенов в секретах. Деплой привязан к environment `github-pages`, поэтому в интерфейсе виден URL и история публикаций.

`concurrency: pages-${ref}` с `cancel-in-progress: true` не даёт двум сборкам одной ветки гоняться за один артефакт.

### 6.4 Почему сборка в CI, а не «собрать локально и запушить `dist`»

- невозможно забыть пересобрать: публикуется только то, что прошло проверки;
- в истории репозитория нет мегабайтов сгенерированного HTML;
- PR показывает, что именно изменится, до слияния;
- сборка воспроизводима на чистой машине.

Навигация повторяет привычную структуру старого сайта: Мир · Этносы · Ходы · Карты · Таблицы · Постройки · Рассадка · Лог · Ссылки. На мобильном — бургер, на десктопе — строка.

### Прогрессивное улучшение

Все ходы отрендерены в HTML статически. Без JavaScript сайт читается целиком: видны все три хода подряд, все карты, вся летопись. JavaScript добавляет только удобства — переключение ходов, фильтры, мобильное меню. Отдельный класс `js` на `<html>` включает скрытие неактивных ходов, поэтому при выключенном JS ничего не пропадает.

## 9. Сценарии сопровождения

### Новый ход

1. Мастер присылает текст и карту.
2. Карта кладётся в `assets/img/map-political-915.png`, в `data/maps.json` добавляется запись.
3. Создаётся `data/turns/915.json` — копия предыдущего файла с новыми событиями.
4. Локально: `python scripts/validate.py && python build.py`.
5. Коммит: `Добавлен 4-й ход (915 г.)`.
6. CI проверяет, собирает, публикует. Лог дополняется этим коммитом автоматически.

Время: 10–15 минут, из них большая часть — перенос текста.

### Новая карта

Запись в `data/maps.json` + файл в `assets/img`. Страница «Карты», превью на главной и ссылки в ходах появляются сами.

### Новый народ

Запись в `data/ethnoses.json` с уникальным `id` и цветом. Карточка, список на главной и раздел «Этносы» обновятся автоматически.

### Исправление опечатки

Правка одной строки в JSON. Никаких других файлов.

### Откат

`git revert` коммита. Следующая сборка вернёт прежнее состояние; лог покажет откат как обычную запись.

### Смена обложки

Поле `hero_map` выбирается в `build.py` по `id` карты — достаточно поменять `id` или добавить карту с нужным идентификатором.

## 10. Лог изменений

Лог — не отдельная ручная страница, а производная от истории репозитория.

1. `scripts/changelog.py` читает `git log -- data` и превращает коммиты в записи `{date, text}`.
2. Записи сливаются с курируемыми (`data/changelog.json`), дубликаты отбрасываются по паре «дата + текст».
3. Сортировка — от новых к старым, ограничение — 100 записей.
4. CI запускает скрипт перед сборкой; в репозиторий результат не коммитится.

Коммит, который создаёт `data/site.json` (первичная публикация сайта), в лог не попадает: это запуск проекта, а не изменение игровых данных. Merge-, revert- и WIP-коммиты тоже пропускаются.

Правила для коммитов, которые должны попасть в лог:

- писать по-русски и по существу: `Добавлен 4-й ход (915 г.)`, `Обновлена политическая карта`;
- технические правки (стили, рефакторинг) не трогают `data/` и потому в лог не попадают автоматически.

Это снимает главную проблему старого сайта: лог больше не нужно помнить — он следствие работы.

## 11. Локальная работа

```bash
python build.py                  # сборка dist/
python scripts/validate.py       # проверка данных
python scripts/validate.py --dist  # проверка ссылок в собранном сайте
python scripts/changelog.py      # дополнить лог из git
python -m http.server 8000 -d dist
```

Требуется только Python 3.9+. Ни `npm install`, ни виртуального окружения, ни интернета.

Быстрая проверка перед коммитом:

```bash
python scripts/validate.py && python build.py && python scripts/validate.py --dist
```

## 12. Качество

### Доступность

- семантическая разметка: `header`, `nav`, `main`, `article`, `figure`, `time`;
- один `<h1>` на страницу, иерархия заголовков без пропусков;
- skip-link, `aria-current` для активного пункта, `aria-expanded` для меню;
- `alt` у содержательных изображений, пустой `alt` у декоративных;
- контраст текста и фона проверен для основных пар (олива/бумага, янтарь/олива);
- поддержка `prefers-reduced-motion`;
- сайт работает без JavaScript и без CSS-анимаций.

### SEO

- `title` и `description` у каждой страницы;
- Open Graph и Twitter Card с изображением 1200×630 (`assets/img/og.jpg`);
- `sitemap.xml`, `robots.txt`;
- ЧПУ-имена файлов, стабильные якоря (`#turn-2`, `#map-political-900`);
- осмысленный `404.html`;
- `.nojekyll`, чтобы GitHub Pages не пытался обрабатывать сайт Jekyll-ем.

### Производительность

- нет веб-шрифтов и внешних библиотек;
- CSS ≈ 35 КБ, JS ≈ 10 КБ, изображения отдаются как есть;
- `loading="lazy"` для карт и галереи;
- статика отдаётся с CDN GitHub Pages;
- сборка — доли секунды, деплой — около минуты.

## 13. Безопасность и права

- В репозитории нет секретов: деплой через OIDC.
- Нет пользовательского ввода и серверной логики — поверхность атаки минимальна.
- Изображения и тексты принадлежат мастеру и участникам партии; код — MIT.
- Публикуются только материалы, которые мастер уже открыл в хронике.
- Персональные данные участников (ники) не дублируются сверх того, что есть на карте рассадки.

## 14. Ограничения и дорожная карта

### Что уже сделано (MVP)

- единый источник данных и генератор;
- одиннадцать страниц, включая летопись, ходы и справочник построек;
- валидация данных и ссылок;
- 36 тестов движка и сборки;
- поиск по всей хронике, фильтры, переходы между ходами, статистика событий;
- лог из git;
- CI/CD на GitHub Pages — сайт опубликован;
- адаптивная вёрстка и работа без JS.

### Честные ограничения

1. **Перенос из docx/форума — ручной.** `data/` — это курируемая выжимка, а не автоматический импорт. Это осознанный компромисс: имена, титулы и даты требуют человеческой проверки.
2. **Рассадка не расписана по игрокам.** Источник — карта и хроника; дублировать список вручную концепция запрещает.
3. **Карта 3-го хода отсутствует** — опубликована только в хронике мастера, сайт честно об этом пишет.
4. **Поиск работает по загруженной странице** — без отдельного индекса. При сотнях событий понадобится предварительная сборка индекса.

### Следующие шаги

| Этап | Что даёт | Сложность |
| --- | --- | --- |
| JSON Schema + `jsonschema` в CI | строгая проверка типов и обязательных полей | низкая |
| `scripts/import_docx.py` | черновик хода из docx за один запуск | средняя |
| Поиск по событиям (клиентский индекс) | быстрый доступ к именам и битвам | низкая |
| Decap CMS / Sveltia | редактирование без git для мастера | средняя |
| Импорт из DM.AM | автоматическая подтяжка ходов | высокая (нестабильный HTML) |
| Тёмная тема | комфорт чтения | низкая |

Порядок выбран так, чтобы каждый этап не ломал текущую схему: данные уже отделены, поэтому инструменты можно добавлять по одному.

## 15. Почему не другие варианты

| Вариант | Почему не подходит |
| --- | --- |
| **Jekyll / Hugo** | Контент пришлось бы раскладывать по Markdown-файлам с front matter; игровые сущности (народы, события, карты) плохо ложатся в «страницы». Нужен Ruby/Go. |
| **Next.js / Nuxt** | SSR и SPA избыточны для статической хроники; появляются Node-зависимости, сборка и обновления безопасности. |
| **Готовая CMS + БД** | Сервер, оплата, бэкапы — против исходного «дёшево и навсегда». |
| **Google Docs / Notion** | Нет версионирования в git, нет валидации, нет единого вида, тяжело встраивать карты. |
| **Оставить как было** | Дублирование и ручной лог уже стоили времени; каждый новый ход — правка больших JS-файлов. |

Выбранный путь — «данные + тонкий генератор + CI» — даёт максимум предсказуемости при минимуме инфраструктуры.

## Итог

Концепция сводится к трём фразам:

1. **Контент живёт в одном месте** — в маленьких JSON-файлах, которые понимает и человек, и скрипт.
2. **Страницы — функция от данных** — их нельзя забыть обновить, потому что они не хранятся отдельно.
3. **Публикация — автоматическая** — GitHub Actions проверяет, собирает и выкладывает сайт; лог пишется историей, а не памятью.

Старый сайт дал стиль и структуру. Новая схема даёт то, чего ему не хватало: предсказуемость обновлений.
